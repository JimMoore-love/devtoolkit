# DevToolkit 工程优化方案

- **对象**：`E:\ai_tools\devtoolkit-app` · DevToolkit v1.5.0（Tauri 2 + Vue 3）
- **体检日期**：2026-10-08
- **方法**：全量源码走读 + `cargo check` / `cargo test` 实测 + 目录与依赖盘点
- **结论一句话**：**代码是好的，烂的是工程底座。** 先修底座，再谈重构。

---

## 摘要：先纠正一个归因

你的判断方向对（项目确实有问题），但归因偏了 —— 问题不在代码。

```
cargo check   →  0 条告警
cargo test    →  99 个测试全过（lib 92 + MCP bin 7），1.3 秒
直接依赖      →  5 个
```

注释在解释「为什么」而不是「是什么」；`control_proto.rs` 用枚举 + 穷举 `match`，把「加了命令
忘了加分支」变成**编译错误**；`api.js` 里甚至写明「这里与后端 `parse_port_spec` 同源，
自检脚本会比对」。这是有工程意识的写法。

真正的病灶是这四条：

1. **项目从未进过版本控制**（无 `.git`）
2. **从零构建是失败的** —— 清一次 `target` 就编不出来
3. **8.8 G 构建产物留在源码树里**，其中一个 `target2` 没有任何配置引用它
4. **零文档** —— 无 README / CHANGELOG / docs

一句话：**这是一个"只能活在作者这台机器上"的项目。**
你那 99 个测试、12 个自检脚本、24 个诊断脚本是真正的资产，但今天它们只存在于一块硬盘上。

## 二、问题清单

### P0 · 工程底座（不修这个，做其他都是白干）

#### P0-1 · 没有版本控制

**证据**：`git rev-parse --is-inside-work-tree` → 退出码 128；根目录无 `.git`；无 `.gitignore`。

**代价**：今天改坏一处，没有 `git diff` 可看，没有 `git stash`/`git checkout` 可退。
`src-tauri/target2`（3.2 G，9 月 11 日）没有任何配置引用它 —— 这类目录通常就是
「手工复制整个目录当版本管理」留下的。**一次「备份」= 3.2 G。**

> 这是投入产出比最高的一条：半小时，换回一辈子的可回滚。

#### P0-2 · 从零构建失败（已定位根因，已实测修复）

**复现**（用任意全新空目录做 target）：

```bash
CARGO_TARGET_DIR=<空目录> cargo check
```

```
error[E0107]: struct takes 3 generic arguments but 2 generic arguments were supplied
  --> ...\schemars-0.8.22\src\lib.rs:12:32
   |
12 | pub type Map<K, V> = indexmap::IndexMap<K, V>;
   |                                ^^^^^^^^ expected 3 generic arguments
note: struct defined here, with 3 generic parameters: `K`, `V`, `S`
  --> ...\indexmap-1.9.3\src\map.rs:76:12
76 | pub struct IndexMap<K, V, S> {
```

**根因链**（逐层查证）：

1. `tauri-build`（**build-dependency**）→ `schemars 0.8.22`（其 `preserve_order` feature 开着）
   → `indexmap 1.9.3`
2. `indexmap` 的 `build.rs`：

   ```rust
   match std::env::var_os("CARGO_FEATURE_STD") {
       Some(_) => autocfg::emit("has_std"),                // 显式开了 std 才走这条
       None    => autocfg::new().emit_sysroot_crate("std") // 否则去探测目标有没有 std
   }
   ```

3. `indexmap 1.9.3/src/map.rs`：

   ```rust
   #[cfg(has_std)]           pub struct IndexMap<K, V, S = RandomState> { .. }
   #[cfg(not(has_std))]      pub struct IndexMap<K, V, S> { .. }   // ← 默认参数没了
   ```

4. **ServBay 分发的 rustc 的 sysroot 布局让 `autocfg` 探测返回假** → `has_std` 不生效 →
   `IndexMap` 失去默认泛型参数 → schemars 8 年前的写法编不过。

**为什么你本机还能编**：`src-tauri/target` 里缓存着 8 月 20 日那次成功的构建产物，
cargo 没有重新编译 schemars，于是这个雷被缓存盖住了。**清一次 `target` 就再也编不出来。**

**修复**（已实测通过，见文末「已落地的改动」）：在 `[build-dependencies]` 里显式开
`indexmap` 的 `std` feature，让 build.rs 走 `Some(_)` 分支跳过探测。

> 注意必须写在 `[build-dependencies]`。写在 `[dependencies]` 无效 ——
> resolver v2 下 build-deps 与普通 deps 的 feature **不合并**（这一条我踩过并验证过）。

### P1 · 结构债务

#### P1-1 · `main.rs` 2692 行，一个文件装 9 个领域

文件内部**分区是清晰的**（有 `// ---------------- xxx ----------------` 分隔），
但 9 个领域挤在一起：

```
  25–296   数据模型（Project / Config / *Result / AppState / 全部常量）
 296–400   helper（lockx / now_* / config 读写 / with_config）
 400–445   系统命令（sys_info / list_ports）
 445–710   端口保护 + kill_pid_scoped（含 KillScope 闸门）
 710–1470  任务运行（端口解析 / 项目校验 / 运行态判定 / spawn / start / stop / takeover）
1470–1630  命令执行（超时 + 双管道并发读）
1630–1695  网络工具箱 command 薄层
1695–1914  MCP 控制口命令 + 功能管理
1916–2037  main()（Builder / setup / 事件）
2038–2692  654 行单元测试
```

**为什么值得拆**：不是「长」，是**改动耦合**。想改端口校验要翻到 756 行，
想看运行态判定要翻到 975 行，两处相隔 200 行却共享 `MAX_PORT_RANGE_SPAN`。

**为什么成本低**：已有清晰分区 + 99 个测试兜底 → 可以**纯搬运、零逻辑改动**，
每搬一个模块跑一次 `cargo test`，99 个必须全绿。

#### P1-2 · 三套端口解析，规则互相矛盾（**唯一已确认的功能性缺陷**）

| 规则 | `main.rs::parse_port_spec`（项目声明端口） | `network.rs::parse_ports`（端口扫描工具） |
|---|---|---|
| 分隔符 | `,` `;` 空白 | `,` **`，`** 空格 |
| 区间跨度上限 | **256**（`MAX_PORT_RANGE_SPAN`） | **2000** |
| 端口 0 | 拒绝（`parse_port_num` 拦） | 接受 |
| 去重 | 是 | 是 |

**用户实际感受**：

- 在「网络工具箱 → 端口扫描」里写 `1-2000` → ✅ 能跑
- 在「项目管理 → 端口声明」里写 `3000-4000` → ❌ 报「跨度过大，最多 256 个」

**同一个 App，两套规则，界面上没有任何地方解释为什么。**
（前端 `api.js::parsePortSpec` 是刻意的第三份镜像，但它有注释 + 自检脚本保证同步，这个可以保留。）

## 三、优化方案

按**投入产出比**排序，四步。每一步都能独立收尾，不要求一次做完。

### 第 0 步 · 让项目"可复现"（今天，约 1 小时）

**收益最大的一步。做完这步，后面所有改动都可回滚。**

1. **先清垃圾**（清完再 init，首提交才是干净的）
   ```
   删：src-tauri/target2（3.2 G，无引用）
       target-ctx（1.8 G）
       vite.config.js.timestamp-*.mjs（3 个）
   留：src-tauri/target（在用的，由 .gitignore 挡住）
   ```
2. **写 `.gitignore`**（放仓库根，或 `src-tauri/` 各一份）
   ```
   node_modules/
   dist/
   src-tauri/target*/
   src-tauri/gen/schemas/
   __pycache__/
   *.pyc
   .shots/
   vite.config.js.timestamp-*.mjs
   ```
3. **`git init` + 首次提交**
   - 先 `git add -A` 后 **`git status` 复核一次**：确认没有 `target/`、`node_modules/` 进去
   - 首提交信息建议写清基线：`chore: 首次纳入版本控制（v1.5.0）`
4. **补 `rust-toolchain.toml`**（把「哪个 rustc 能编过」这件事写进仓库）
   ```toml
   [toolchain]
   channel = "1.95.0"
   ```
   > 这一步的意义：换一台机器、换一个 rustc 发行版时，构建不再靠运气。
   > 当前 P0-2 的坑本质就是「工具链差异没人管」。
5. （可选，建议）推一份到 GitHub private —— 有了远端，才真的不会丢。

**验收**：`git status` 干净、仓库体积 < 20 M、`git log` 有一条基线提交。

**铁律：不改任何逻辑，只搬位置。每搬一个模块跑一次 `cargo test`（99 条必须全绿）。**

目标结构：

```

├── main.rs              →  只剩 main()：Builder / setup / 窗口事件（≤150 行）
├── lib.rs               →  模块声明 + pub use（Tauri 建议有 lib，测试更好写）

├── task/
│   ├── runner.rs        →  spawn_task / start_task / stop_task / list_tasks
│   ├── takeover.rs      →  takeover_project / TAKEOVER_RELEASE_WAIT_MS
│   └── exec.rs          →  run_command_with_timeout / pump_output / take_buf / join_bounded
```

## 四、不建议做的事（避免过度重构）

明确写出来，防止把「优化」做成「重写」：

- ❌ **不要拆 `network.rs`**。它 1658 行，但内部按协议清晰分区，附带 28 个测试，
  是「自包含的解析层」。动它是纯风险。
- ❌ **不要换框架 / 换状态管理**。Vue 3 + `reactive` store 在这个体量完全够用。
- ❌ **不要把 `main.rs` 的 654 行测试挪走**。它们贴着被测代码，是有意为之；
  拆模块时测试跟着模块走即可。
- ❌ **不要为「好看」重命名现有函数**。改名会污染 diff，让「有没有改逻辑」无法复核。
- ❌ **不要引入任何新的运行时依赖**来解决问题。当前 5 个直接依赖是巨大优势。

### 统一后的规则（取并集，任何历史配置都不会失效）

- 分隔符：`, ; ， ； |` + 任意空白
- 端口号：1–65535 十进制整数（拒绝 0 / `+80` / `-1` / `65536`）
- 跨度上限：**2000**（按**个数**算，`1-2000` 合法）
- 顺序：书写顺序 + 去重
- 非法项：宽松路径跳过、严格路径报错（**判定逻辑共用，只在「怎么办」上分叉**）

### 为什么上限取 2000 而不是 256

256 会让端口扫描既有的 `1-2000` 写法直接失效（能力退化）；2000 只是把项目声明端口的上限**放宽**，
不破坏任何现有配置，且 2000 端口在 64 并发 / 1.2s 超时下最坏约 38 秒，仍在可接受范围。
`runtime_by_ports` 是纯内存 `contains` 查询，放宽不影响刷新速度。

### 防漂移机制（关键）

`ports.rs` 里声明了一张 `SHARED_CASES` 用例表（20 条，宽松路径的输入→期望）。
`npm run check:guards` 会**把这张表从 Rust 源码里抠出来，逐条喂给前端实现** ——
两侧对着同一份声明式契约校验，不需要维护第三份副本。另外还断言：

- 跨度上限常量两侧一致、分隔符集合两侧一致
- `network.rs` 的 `parse_ports` 确实已委托、且不再自带分隔符表
- `api.js` 确实在 re-export、且没有第二份实现
- 全仓扫描：除 `portSpec.js` / `api.js` 之外不许再出现解析特征（防第 6 份副本）
